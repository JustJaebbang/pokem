# 포켐 Flutter 앱

현재 단계는 로그인·회원가입·홈·상품 조회·사진 포함 상품 등록·관심상품·채팅·구매 결제·구매내역·구매확정·포켐머니 충전·환전·판매내역입니다. 제공된 시안의 아이콘·아이디·비밀번호·자동로그인·로그인·회원가입 배치를 바탕으로 구현했습니다.
회원가입은 서버에 연결되어 있으며, 계정 찾기는 후속 구현 안내만 표시합니다. 일반 사용자는 로그인 후 상품 홈으로, 매니저·디렉터는 계정 확인 화면으로 이동합니다.

## 구조: MVVM + Riverpod

```text
lib/
  model/
    auth/                 # 계정·세션, 화면 입력, API 요청 모델
    products/             # 상품·사진, 화면 입력, API 요청 모델
    wishlist/             # 관심상품 응답·목록 모델
  view/
    auth/                 # 로그인·회원가입·계정 확인
    home/                 # 홈 탭 구성·상품 목록 표시
    products/             # 상품 상세·등록
      widgets/            # 상품 이미지 위젯
    wishlist/             # 관심상품 목록·하트 위젯
  vm/
    auth/                 # LoginVm·RegisterVm
      state/              # 로그인·회원가입 화면 상태
    home/                 # HomeShellVm
    products/             # ProductsVm·ProductDetailVm·ProductCreateVm
      state/              # 목록·검색·상세·등록 화면 상태
    wishlist/             # 관심 목록·등록·해제·진행 상태
  repository/
    auth/                 # 세션 정책·저장·인증 데이터 처리
    products/             # 상품 조회·등록 데이터 처리
  service/
    auth/                 # 인증 API 통신
    products/             # 상품 API 통신·기기 사진 선택
  core/
    providers/            # Riverpod 의존성 조립
    config/               # API 서버 주소
    storage/              # 보안 저장소
    formatters/           # 금액 표시
    media/                # 이미지 주소 해석
```

View는 VM 상태를 구독하고 입력을 전달하며 화면 이동·키보드·컨트롤러 수명을 처리합니다.
View에서 데이터 계층 Provider를 읽거나 HTTP를 호출하지 않습니다.
VM은 검증·입력 변환·조회·등록·세션 만료·재시도·등록 후 목록 갱신을 담당합니다.
폼은 VM의 검증 메서드를 호출하며, VM도 제출 시 같은 검증을 수행해 화면 없이 검증 가능합니다.
Repository는 데이터 처리 정책을, Service는 HTTP·기기 API 접근을 담당합니다.
두 계층은 Riverpod과 화면을 모르며 `core/providers/data_providers.dart`가 의존성을 주입합니다.
상세 조회도 ProductDetailVm을 통해 처리하고, 목록과 검색은 ProductsVm의 한 상태로 관리합니다.
자세한 규칙은 [ARCHITECTURE.md](ARCHITECTURE.md)를 참고하세요.

## 개발 실행

FastAPI 저장소 루트에서:

```powershell
python -m uvicorn main:app --host 0.0.0.0 --port 8000
```

서버 .env에 DB 연결 정보와 32바이트 이상의 JWT_SECRET_KEY가 설정되어 있어야 합니다.
서버의 .env는 Flutter에 복사하지 않습니다. 앱에는 API 서버 주소만 설정합니다.

다른 터미널에서 Android 에뮬레이터를 실행하거나 실제 Android 기기를 연결하고:

```powershell
cd flutter_app
flutter pub get
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:8000
```

10.0.2.2는 Android 에뮬레이터에서 개발 PC를 가리키는 기본 주소입니다.
실제 폰에서는 같은 네트워크에 있는 PC의 LAN IP로 바꿉니다.

```powershell
flutter run --dart-define=API_BASE_URL=http://192.168.20.42:8000
```

실제 PC IP가 다르면 그 주소로 바꿔야 합니다. 폰의 localhost는 PC가 아닙니다.
API 주소 변경은 hot reload가 아닌 재실행으로 반영합니다.
Android 디버그 빌드에서만 개발용 HTTP를 허용합니다. 배포 서버는 HTTPS를 사용합니다.
Windows·Web 타깃은 이번에 생성하지 않았습니다. Android 또는 iOS 기기를 선택해야 합니다.
iOS는 macOS/Xcode 환경에서 빌드·실기기 네트워크와 Keychain 동작을 확인해야 합니다.

## 로그인 유지

자동로그인을 선택했을 때만 access token과 만료일시를 flutter_secure_storage에 저장합니다.
아이디·비밀번호와 전체 회원정보는 저장하지 않습니다.
재실행 시 유효기간을 확인하고 GET /auth/me로 계정을 재검증합니다.
만료되거나 서버에서 거부한 토큰은 삭제합니다. 일시적인 통신 오류 시에는 저장 토큰을 유지하며 오류를 표시합니다.
실행 중 만료 시 로그인 화면으로 돌아갑니다. 서버에 refresh token API가 없어 토큰 갱신은 하지 않습니다.
로그아웃은 기기에 저장된 토큰 삭제이며 서버의 토큰 폐기 API를 호출하는 것은 아닙니다.

## 회원가입

로그인의 회원가입 버튼에서 입력 화면으로 이동합니다.
아이디·닉네임·이름·비밀번호·비밀번호 확인·주소·전화번호·이메일을 입력합니다.
비밀번호 확인은 앱에서만 비교하고, POST /user에는 user_id, user_password, user_nickname,
user_name, user_phone, user_email, user_address만 전달합니다. 비밀번호는 공백을 임의로 제거하지 않습니다.
가입 성공 후 로그인 화면으로 돌아가 아이디를 채우고 비밀번호는 비웁니다. 자동 로그인하지 않습니다.
중복 아이디는 가입 요청 시 서버가 409로 응답하며 입력을 유지하고 안내합니다.
주소는 직접 입력하며, 주소 검색·휴대폰 문자 인증·별도 아이디 중복확인 버튼은 아직 연결하지 않았습니다.
연속 제출은 차단하고, 처리 중에는 뒤로가기로 가입 결과를 잃지 않도록 막습니다.
실제 DB에 테스트 회원을 생성하지 않았습니다. 서버의 중복 처리 테스트도 가짜 DB로 검증합니다.

## 홈·상품 조회

일반 사용자 로그인 후 홈·관심·등록·채팅·마이페이지 탭을 표시합니다.
홈은 GET /sell_product로 받은 실제 상품을 이미지·이름·가격·상태와 함께 보여줍니다.
홈은 기본으로 판매중인 상품만 표시하고 거래중·거래완료 상품은 제외합니다.
상태 전환 필터는 제공하지 않으며 상품명·설명·카드 코드 검색도 판매중 상품에만 적용합니다.
이 조건은 현재 API로 받은 목록에 대해 앱에서 적용합니다.
현재 서버가 전체 목록을 반환하므로 서버 검색·페이지네이션은 후속 확장 사항입니다.
브랜드·카테고리·일반/대리판매 구분·공식 검수 여부는 현재 상품 응답에 없어 추정해서 표시하지 않습니다.
상품의 등급은 등록 등급으로만 표시합니다. Unrank는 미지정으로 표시합니다.

상품 선택 시 GET /sell_product/{code}로 상세를 다시 조회해 설명·최신 가격·상태를 표시합니다.
상대 이미지 경로는 API 서버 주소와 합치고, HTTP·HTTPS만 허용하며 실패 시 카드 아이콘을 표시합니다.
당겨서 새로고침, 로딩·빈 목록·오류·수동 재시도를 제공합니다.
마이페이지 탭에서는 로그인한 계정과 역할을 표시하고 로그아웃할 수 있습니다.
상세를 보는 중 로그인 만료 시 상세 경로도 닫고 로그인 화면으로 복귀합니다.
검수신청은 신청내역·수량 입력 화면으로, 구매하기는 결제 화면으로 연결됩니다.
상품 조회에서는 백엔드·DB 변경이나 테스트 상품 생성을 하지 않았습니다.

## 사진 포함 상품 등록

하단 등록 탭은 별도 상품 등록 화면을 엽니다. 사진 한 장과 상품명·설명·가격을 입력합니다.
카드 정보는 레귤레이션·카드 팩 구분·세트 구성·세트 번호·레어도를 직접 입력하는 방식으로 사용합니다. 카탈로그 선택 API와 선택 화면은 만들지 않습니다.
이 다섯 값은 서버가 조합하는 기존 cardinfo_serial_code와 일치해야 합니다. 임의 값은 404로 거부됩니다.
기존 사용자 주소지가 없으면 서버가 등록을 거절합니다. 검수 등급 입력은 제공하지 않으며 서버 기본 Unrank를 사용합니다.

1. 휴대폰 갤러리에서 사진 한 장 선택
2. 등록하기를 누르면 Bearer 토큰으로 POST /sell_product/image에 multipart file 업로드
3. 응답의 sell_product_image를 POST /sell_product JSON에 포함
4. 성공하면 등록 화면을 닫고 홈의 판매중 목록을 새로 조회

사진 취소 시 기존 선택은 유지하고 삭제·교체가 가능합니다.
입력·업로드·등록 오류를 화면에 표시하고 연속 제출을 차단합니다.
사진 업로드 후 상품 등록만 실패하면 같은 화면의 재시도는 기존 업로드 주소를 재사용합니다.
등록 요청 중에는 뒤로가기를 차단합니다. 서버에서 401을 받으면 로그인 상태를 정리합니다.
네트워크 단절 시 서버에서 등록이 완료됐을 수 있어 재등록 전에 홈에서 확인해야 합니다.
서버가 상품 생성용 멱등키를 제공하지 않아 앱에서 자동 재전송하지 않습니다.

서버에 이미지 의존성을 설치한 뒤 재시작해야 합니다:

```powershell
pip install -r requirements-images.txt
```

파일은 서버 uploads/products에 저장하고 /media/products/{filename}으로 공개 조회합니다.
입력 및 저장 이미지는 최대 5MiB, 최대 1,000만 픽셀의 JPEG·PNG·WebP 정지 이미지만 허용합니다.
서버는 실제 형식을 확인하고 메타데이터를 제거한 뒤 새 이름으로 재인코딩합니다.
클라이언트는 선택 시 긴 변을 2400픽셀 이하로 조정하도록 요청하며 5MiB 한도를 확인합니다.
서버 저장 폴더는 재배포 시 보존해야 합니다. 상품 등록 실패·사진 교체로 남은 파일은 자동 삭제하지 않습니다.
운영 프록시에도 업로드 요청 크기 제한을 적용해야 합니다. 앱 서버 검사는 multipart 파싱 후 실행됩니다.

iOS 사진 보관함 접근 설명을 추가했고, Android 사진 선택 중 앱이 종료된 경우의 복구도 호출합니다.
텍스트 입력은 프로세스 종료 후 복원하지 않습니다. 실제 기기 갤러리와 Keychain 동작은 별도 확인해야 합니다.
플러그인 설정 참고: https://pub.dev/packages/image_picker
실제 DB에 상품·회원·이미지 테스트 데이터를 생성하지 않았습니다.

사진 플러그인 추가·변경 후에는 hot reload만으로 네이티브 코드가 반영되지 않습니다. 실행 중인 앱을 중지하고 flutter run으로 다시 빌드·설치해야 합니다. 사진 선택 실패는 업로드 영역 바로 아래에 표시합니다.

## 관심상품

상품 상세 오른쪽 위 하트로 관심 등록·해제를 처리합니다. 하단 관심 탭에 내 관심상품을 표시합니다.
홈은 판매중 상품만 표시하지만, 관심 목록은 판매중·거래중·거래완료 상품을 모두 유지하고 카드에 현재 상태를 표시합니다. 거래중·거래완료 상품도 상세 조회·관심 해제가 가능하며 구매는 판매중일 때만 허용합니다.
상품 카드 하트로 해제하거나 카드를 눌러 상세 화면으로 이동할 수 있습니다.
빈 목록·조회 실패·재시도·당겨서 새로고침을 제공합니다.

- GET /wishlist/{로그인 사용자 ID}: 내 활성 관심상품 코드 조회
- POST /wishlist: sell_product_sell_product_code만 전달하여 등록
- DELETE /wishlist/{로그인 사용자 ID}/{상품 코드}: 해제

요청에는 로그인 토큰을 사용합니다. 사용자 ID는 로그인 세션에서 결정합니다.
서버 응답은 상품 코드만 포함하므로 Repository가 GET /sell_product 결과와 한 번에 합칩니다.
추가 상품 조회를 상품 개수만큼 반복하지 않습니다. 관심 없음이면 상품 목록 조회를 생략합니다.
화면의 하트와 목록은 하나의 WishlistVm 상태를 공유합니다.
하트를 누르면 서버 응답 전에 하트와 목록을 즉시 변경합니다. 요청 중 해당 하트의 연속 클릭은 막고, 실패하면 그 상품만 이전 상태로 복구합니다.
조회와 변경이 겹쳐 상태가 뒤집히지 않도록 처리하며, 로그아웃 뒤 도착한 이전 응답은 반영하지 않습니다.
401 응답은 로그인 만료로 처리합니다. 매니저·디렉터에게 일반 사용자의 관심 기능을 허용하지 않습니다.
백엔드·DB 스키마 변경과 실제 관심 데이터 생성 없이 기존 API에 연결했습니다.

## 채팅

상품 상세의 채팅하기 버튼은 POST /chat_room으로 기존 방을 재사용하거나 새 방을 만듭니다.
본인 상품 문의·판매 종료 후 새 문의 등은 서버의 409 메시지를 표시합니다.
하단 채팅 탭에서 GET /chat_room 목록을 50개씩 조회하며 당겨서 새로고침·더 보기를 제공합니다.
현재 API에는 상대 닉네임·프로필 이미지·마지막 메시지·읽음 정보가 없어 상품 제목과 상대 ID를 표시합니다.
일반 사용자만 접근하며 관리자는 사용자 간 대화를 열람하지 않습니다.

대화방에 들어가면 상세를 확인하고 WebSocket에 연결합니다.
인증 토큰은 URL에 넣지 않고 첫 프레임 {type: auth, access_token: ...}으로 전송합니다.
ready 후 메시지 이력을 after_chat_seq와 limit=100으로 끝까지 조회하고 실시간 메시지와 순번으로 병합합니다.
실시간 메시지가 이력보다 먼저 도착해도 누락되지 않도록 이력 커서를 별도로 유지합니다.
연결 단절 시 2·4·8·16·30초 간격으로 재연결하며 누락된 이력을 복구합니다. 다시 연결 버튼도 제공합니다.
권한 상실·토큰 만료는 자동 재시도를 중단하며 401은 로그인 화면으로 돌려보냅니다.
화면을 닫으면 연결·구독·재연결 및 전송 타이머를 정리합니다.

메시지는 공백만 아닌 1~500자 텍스트만 전송합니다. 저장 완료 이벤트를 받은 뒤 말풍선에 표시하고 입력을 비웁니다.
서버 확인 전에는 중복 전송을 차단하며, 전송 중 연결이 끊겨도 내용을 자동 재전송하지 않습니다.
재접속 이력에서 저장이 확인되면 입력을 비우고, 확인되지 않으면 입력을 유지해 사용자가 판단하게 합니다.
사용자 요청 ID 기반 서버 멱등 처리는 아직 없어 전송 결과가 불확실할 때 반복 전송하면 중복될 수 있습니다.
종료된 방은 이력만 조회하고 전송하지 않습니다. 날짜·시각은 기기 현지 시간으로 표시합니다.
사진 메시지·푸시 알림·읽음 표시·실시간 방 목록 갱신은 포함하지 않았습니다. 방 목록은 진입·새로고침으로 갱신합니다.

현재 전송 관리자는 서버 프로세스 메모리를 사용하므로 FastAPI는 --workers 1로 실행합니다.
HTTP 서버 주소가 HTTPS면 WebSocket도 WSS를 사용합니다. 이 앱은 Android/iOS 네이티브 WebSocket을 사용합니다.
테스트는 가짜 Repository와 로컬 실제 WebSocket 서버로 수행했으며 운영 DB에 테스트 방·메시지를 생성하지 않았습니다.
실제 계정 두 개로 양쪽 기기 송수신·재접속을 추가 확인해야 합니다.

## 구매·결제

상품 상세의 구매하기에서 최신 상품과 내 포켐머니 잔액을 조회합니다.
등록된 주소는 참고 표시이며 이번 구매 요청에서 배송지로 저장하거나 delivery를 생성하지 않습니다.
상품·결제금액 확인을 선택한 뒤 결제하면 POST /purchase_item으로 상품 코드와 expected_price를 보냅니다.
사용자 ID·차감 금액·상품 상태는 서버가 결정합니다. 잔액 부족은 앱에서 안내하며 서버에서도 다시 검사합니다.
서버는 상품 잠금 후 expected_price와 현재 가격이 다르면 409로 거절합니다.
이 필드는 선택 사항이므로 기존 클라이언트의 요청도 유지됩니다. DB 스키마 변경은 없습니다.

결제 성공 후 홈·상세·관심상품·구매내역을 갱신합니다. 구매 성공 상태는 거래중이며 거래완료가 아닙니다.
응답 유실·서버 오류 시 자동 재결제하지 않고 결제 결과 확인으로 내 구매내역을 조회합니다.
아직 기록이 보이지 않아도 처리 중일 수 있어 같은 화면에서 결제를 다시 허용하지 않습니다.
앱 재실행을 넘는 결제 요청 식별자·멱등키는 현재 서버에 없으며 후속 확장 대상입니다.

마이페이지 탭과 결제 완료 화면에서 구매내역에 접근합니다.
구매 목록·단건 조회 응답에 상품 제목·이미지·실제 결제 금액이 포함됩니다. 구매내역 화면은 이미지·제목·금액·구매 시간·상태를 표시합니다.
금액은 cybermoney_pay의 구매 당시 결제 금액이며 현재 상품 가격으로 대체하지 않습니다.
상품 제목·이미지는 연결된 sell_product의 현재 정보이며 구매 당시 스냅샷은 아닙니다.
상품 정보나 결제 기록이 없으면 내역을 유지하고 각각 상품 정보 없음·금액 확인 불가로 표시합니다.
상품을 누르면 상세로 이동합니다. 구매취소 신청·철회는 아래 흐름으로 연결합니다.
배송비·수수료·약관 동의는 실제 API·정책이 연결되기 전 임의로 추가하지 않았습니다.
실제 DB에 구매·결제 테스트 데이터를 만들지 않고 가짜 응답과 DB로 검증했습니다.

## 포켐머니 충전·환전

마이페이지 탭의 포켐머니에서 최신 잔액과 충전·환전 내역을 조회합니다.
구매 화면의 충전하기로 진입한 경우 돌아왔을 때 결제 잔액을 다시 조회하고 금액 확인을 다시 받습니다.
은행명·계좌번호는 직접 입력하며 서버의 45자 한도에 맞춥니다.
1만·5만·10만원 추가 버튼과 숫자 입력을 제공하고, 확인 대화상자 후 요청합니다.

- GET /user/{내 ID}: 잔액
- GET /recharge, GET /exchange: 내 충전·환전 내역
- POST /recharge: recharge_account, recharge_price
- POST /exchange: exchange_account, exchange_price

로그인 토큰을 전달하며 요청 본문에 사용자 ID를 넣지 않습니다.
양의 정수·DB INT 범위·충전 후 잔액 한도·환전 잔액을 VM에서 확인하고 서버가 최종 검증합니다.
성공 시 서버가 반환한 잔액을 표시하고 지갑 내역을 새로 조회합니다. 구매 성공 시에도 지갑을 갱신합니다.

현재 API는 실제 결제 승인·입금 확인·은행 송금을 수행하지 않습니다.
충전은 앱 잔액 증가, 환전은 요청 기록과 잔액 차감만 처리하며 화면에도 이를 안내합니다.
실제 은행 계좌 선택·등록 API는 없어 계좌 선택 목록을 만들지 않습니다.
충전·환전 내역에는 서버에 없는 승인·송금 완료 상태를 표시하지 않습니다.

서버에 멱등키가 없으므로 전송 중 재요청을 차단합니다.
응답 유실·5xx·해석 불가능한 성공 응답은 결과 불확실 상태로 유지하고 내역을 확인하도록 안내합니다.
같은 로그인 세션에서는 화면을 닫았다 열어도 요청을 다시 보내지 못합니다.
동일 금액·계좌의 내역만으로 해당 요청 성공을 단정하지 않으며, 결과 불확실 상태를 자동 해제하지 않습니다.
앱 종료·재로그인 이후까지의 중복 방지는 서버 요청 ID·멱등 처리 도입이 필요합니다.
계좌 입력은 앱 메모리에만 보관하고 로그·기기 저장소에 저장하지 않습니다.
운영 DB에 테스트 충전·환전을 실행하지 않았습니다.

## 구매확정

마이페이지 → 구매내역에서 거래중 상품의 구매확정 버튼을 누릅니다.
상품 수령 확인과 판매자 대금 지급 안내를 읽고 확인해야 요청합니다.
VM은 GET /purchase_item/{구매번호}로 최신 상태를 확인한 뒤
POST /purchase_item/{구매번호}/confirm을 호출합니다. 사용자 ID·판매자·지급 금액은 보내지 않습니다.
서버가 본인 구매·결제 완료·취소 요청 여부·잔액 한도 등을 검사하고 판매대금 지급과 거래완료 처리를 원자적으로 수행합니다.

이미 구매확정된 내역은 재요청하지 않고, 취소 요청 중·취소된 내역에는 확정 버튼을 표시하지 않습니다.
서버의 구매 상태 구매확정은 화면에서 거래완료로 표시하며 완료한 카드에 구매확정 완료를 표시합니다.
성공 시 구매내역·상품 상세·홈·관심상품·지갑을 갱신합니다.

전송 중에는 같은 구매 건에 다시 요청하지 못합니다.
전송 후 응답 유실·5xx·해석 불가 응답이면 같은 세션에서 화면을 닫아도 결과 불확실 상태를 유지합니다.
처리 상태 확인 버튼은 단건 GET만 호출하고, 구매 상태와 확정 일시로 성공을 확인합니다.
아직 거래중이라고 응답해도 처리 중일 수 있어 자동으로 POST를 반복하지 않습니다.
401은 로그아웃 처리하고, 서버의 403·409 등의 오류 안내를 표시합니다.
기존 구매확정 API를 사용하므로 서버·DB 구조 변경은 없으며 실제 DB 구매확정·판매자 지급 테스트는 실행하지 않았습니다.

상품 상세 API의 seller_user_id는 일반판매·대리판매의 실제 소유자를 반환합니다.
로그인한 사용자와 소유자가 같으면 채팅하기·구매하기 하단 영역을 표시하지 않습니다.

## 판매내역

마이페이지 → 판매내역에서 본인의 일반판매·대리판매를 함께 조회합니다.
GET /sale_history는 일반 사용자 인증이 필요하며 로그인 사용자 ID로만 필터링합니다.
기존 관리자용 GET /post_item과 대리판매 API는 유지합니다.

이미지·상품 제목·판매 방식·현재 상태·등록 또는 거래완료 일시를 표시합니다.
판매중은 현재 판매가, 거래중·거래완료는 취소되지 않은 구매 건의 실제 결제 금액을 표시합니다.
결제 기록이 없거나 중복되어 금액을 확정할 수 없으면 금액 확인 불가를 표시합니다.
상품 정보가 누락되어도 판매등록 내역은 유지합니다. 제목·이미지는 현재 상품 정보입니다.
일반판매의 한국 시간 일시와 대리판매 ISO 일시를 시간대 포함 형식으로 통일하여 최근 순으로 반환합니다.
상품 카드를 누르면 상세로 이동하며, 당겨서 새로고침·오류 재시도·빈 내역을 지원합니다.
실시간 자동 갱신·기간 필터·페이지네이션·상품 수정은 이번 범위에 포함하지 않습니다.
추가 API 반영을 위해 서버를 재시작해야 하며 DB 구조 변경은 없습니다.
검증은 가짜 응답과 메모리 DB로 수행했고 실제 MySQL에서는 EXPLAIN으로 쿼리만 검증했습니다.

마이페이지 탭의 판매·구매 스위치는 기본 판매 모드이며, 판매에서는 판매내역·취소 요청, 구매에서는 관심상품·구매내역을 표시합니다.
선택 상태는 MypageVm이 관리하고 탭을 이동해도 유지하며 계정 변경 시 판매로 초기화합니다.

기존 서버 API를 사용하므로 서버·DB 구조 변경은 없습니다. 실제 DB의 회원정보 수정 테스트는 실행하지 않았습니다.

## 검수신청

홈의 검수신청 또는 마이페이지 → 검수신청 내역에서 신청내역을 확인하고 새 신청을 만듭니다.
GET /inspection_request는 로그인한 사용자의 신청만 반환합니다.
POST /inspection_request에는 양의 정수 inspection_request_amount만 보내며 사용자 ID는 서버가 결정합니다.
성공하면 신청번호·수량을 표시하고 신청내역을 갱신합니다.
목록에는 신청일·수량·담당자 배정 여부만 표시하며 담당자 배정을 검수 진행 상태로 간주하지 않습니다.
서버의 한국 시간 신청일을 시간대가 있는 형식으로 해석해 기기 시간으로 표시합니다.

제출 중·성공 후 중복 신청을 막으며, 정상 접수 후 추가 신청 버튼으로 새 건을 작성할 수 있습니다.
응답 유실·5xx·해석 불가 성공 응답은 결과 불확실 상태로 유지하고 같은 세션에서 화면 재진입 시에도 자동 재요청하지 않습니다.
신청내역을 확인하도록 안내하되 같은 수량·일시만으로 특정 요청의 성공을 단정하지 않습니다.
서버에 멱등키가 없어 앱 종료·재로그인 이후까지의 중복 방지는 후속 확장이 필요합니다.
검수 결과 조회·반환/대리판매 선택은 아래 흐름으로 연결하며, 검수비 결제는 후속 화면입니다.

PATCH /pay/{pay_no}는 기존 관리자 전용으로 유지합니다.
새 완료 API 반영을 위해 서버 재시작이 필요하며 DB 구조 변경은 없습니다. 검증 중 실제 DB의 결제 상태는 변경하지 않았습니다.

상품 상세 응답에 sale_type(direct/consign)를 추가했고 기존 seller_user_id와 함께 수정 가능 여부를 판정합니다.
PUT /sell_product/{code}는 기존 소유권 검사를 유지하며 서버에서 상품 행을 잠근 뒤 판매중 상태를 확인합니다.

저장 중 중복 제출·뒤로가기를 막고 실패 시 입력을 유지하며 권한·상태 오류 후에는 최신 조회를 요구합니다.
성공하면 홈·상품 상세·관심상품·판매내역을 갱신하고 수정 화면을 닫습니다.

서버 응답·상태 검사 반영을 위해 재시작이 필요하며 DB 구조 변경이나 실제 상품 갱신 테스트는 실행하지 않았습니다.

## 상품 수정 사진 교체

선택한 사진을 미리 보여주며 기존 사진 사용으로 되돌릴 수 있습니다. 선택 창에서 취소하면 직전 선택을 유지합니다.

사진 업로드 후 상품 수정만 실패하면 같은 화면의 재시도에서 업로드 주소를 재사용합니다.
다른 사진을 선택하면 캐시된 주소를 초기화하고 원본 복귀 시 선택·업로드 주소를 모두 지웁니다.

업로드 후 로그아웃·세션 변경이 확인되면 상품 수정 요청을 보내지 않습니다.

기존 업로드 파일을 자동 삭제하지 않으며 앱 종료 후 사진 선택과 입력을 영구 복원하지 않습니다.
검증은 가짜 사진 선택·업로드·저장 응답으로 수행했고 실제 상품 사진은 변경하지 않았습니다.

### 거래취소 승인 후 자동 판매 재개

### 배송 조회

- 현재 API에는 원본별 검색 필터·운송장 정보가 없어, 오래된 배송 조회 시 여러 목록 요청이 발생할 수 있으며 택배사 실시간 추적은 지원하지 않습니다.

### 회원탈퇴

- 마이페이지 → 회원탈퇴에서 잔액과 탈퇴 안내를 확인하고, 동의 체크 및 최종 확인 후 기존 `DELETE /user/{user_id}`를 호출합니다. 사유는 선택 입력(최대 200자)입니다.
- 서버에서 사용자 행을 잠근 후 잔액이 0원이 아니면 탈퇴를 거절합니다. 앱에서 확인한 후 잔액이 바뀌어도 서버가 다시 검증합니다.
- `user`와 기존 거래·이용 기록은 보존하고 `quit`에 탈퇴 일시·사유만 저장합니다. 거래내역이 있다는 이유로 사용자 삭제의 외래 키 오류가 발생하지 않습니다. 중복 탈퇴는 사용자 행 잠금 및 quit 기록 조회로 차단합니다.
- quit 기록이 있는 사용자는 로그인과 기존 JWT 인증을 거절합니다. WebSocket도 접속·수신 재인증과 메시지 저장 시 차단합니다. 기존 user ID가 유지되므로 동일 ID 재가입은 허용되지 않습니다.
- 성공 시 로그인 정보와 메모리 세션을 정리합니다. 저장소 삭제 실패 시에도 탈퇴한 계정의 로그인 상태를 복원하지 않습니다.
- 결과가 불명확하면 중복 DELETE를 차단하고 조회로 상태를 확인합니다. 계정이 조회되지 않거나 인증이 거절되면 로그인 화면으로 이동하며 탈퇴 성공으로 단정하지 않습니다.
- MVVM/Riverpod을 사용하며 DB 스키마 변경이나 실제 사용자 데이터 변경은 수행하지 않았습니다. 테스트용 SQLite에서 사용자·거래 기록 보존과 인증 차단을 검증했습니다.

- 결제·선택·취소 처리 후, 연결 화면에서 복귀하거나 마이페이지 탭에 다시 진입할 때 갱신합니다. 카드의 새로고침으로도 확인할 수 있습니다. 조회 실패는 0건과 구분합니다.
- 마이페이지 탭에서만 조회하며 푸시 알림이나 백그라운드 주기 조회 기능은 아닙니다. DB 스키마와 처리 로직은 변경하지 않았습니다.

### 상단 검색·알림 및 마이페이지 명칭

- 메인 탭 공통 AppBar 우측에 검색(`Icons.search`)과 알림(`Icons.notifications_none`)을 표시합니다. 하단의 나 탭은 마이페이지로 변경했습니다. 관심 탭 본문에는 관심목록 제목을 표시합니다.
- 관심 탭 검색은 관심상품만 검색하며 거래중·거래완료 상태도 유지합니다. 다른 탭 검색은 판매중인 상품을 검색합니다. 상품명·설명·카드 코드를 기존 조회 데이터에서 검색하며 별도 카탈로그 선택 API는 추가하지 않습니다.
- `GET /notifications`는 로그인한 일반 사용자의 검수비 결제 대기, 검수완료 결과, 판매자 취소 요청, 구매자 취소 승인/거절, 실제 취소 환불·판매대금 입금을 최신순으로 조회합니다. 내부 검수 판정 사유는 응답에 포함하지 않습니다.
- 기존 업무 기록에서 알림함을 구성하며 별도 알림 테이블이나 원본 기록 복제는 하지 않습니다. 처리된 결제 대기·판매자 요청은 해당 대기 알림에서 제외되며 변경 전 모든 상태의 영구 이벤트 이력은 아닙니다.
- 개별 읽음·모두 읽음 및 미확인 건수 배지를 지원합니다. 읽음 ID는 기존 secure storage를 사용해 API 서버 주소와 사용자 ID별로 현재 기기에 저장합니다. 기기 간 읽음 동기화는 지원하지 않습니다.
- 알림은 관련 결제·검수 결과·취소 처리·포켐머니 화면으로 이동합니다. 앱 재개, 메인 탭 이동, 업무 처리 완료, 알림함 진입/복귀 및 수동 새로고침 때 갱신합니다.
- 앱 내 알림함이며 OS 푸시·백그라운드 수신·실시간 알림 전송은 포함하지 않습니다. DB 스키마·잔액·처리 로직은 변경하지 않았습니다.

- 홈 본문의 검색 입력창은 제거했습니다. 홈과 관심상품의 검색은 상단 돋보기에서 별도 검색 화면으로 진입합니다. 검색 화면에서 상품 상세를 보고 돌아와도 검색어를 유지하며 홈 상품 목록에는 해당 검색어를 적용하지 않습니다.
