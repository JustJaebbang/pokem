## 의존성 설치 및 실행

프로젝트 루트의 PowerShell에서 실행합니다. Python 3.10 이상 또는 uv가 필요합니다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\setup.ps1
.\.venv\Scripts\python.exe -m uvicorn main:app --reload
```

설치한 가상환경은 VS Code의 Python 인터프리터로 `.venv\Scripts\python.exe`를 선택합니다.
실행 후 `http://127.0.0.1:8000/docs`에서 API를 확인할 수 있습니다.
DB와 JWT 환경변수는 `.env.example`을 참고하여 `.env`에 별도로 설정합니다.
테스트용 의존성까지 설치하려면 설치 명령 끝에 `-IncludeTests`를 추가합니다.

- 사용자가 inspection_request를 넣으면 로그인된 user_id와 수량을 적어서 보내고
  date와 no는 자동 생성된다. 이때 no는 date+{seq:06d}로 생성된다.
  추후 관리자가 확인하면 확인한 관리자의 id가 patch되어 들어간다.

- no 로 생성되는 번호들은 생성번호 길이 초과 문제로 VARCHAR로 수정

- inspection_request가 확인되면 pay가 자동 생성

- 검수 완료시 발생하면 deposit_refund가 생성

```
delivery CR
director CR
case CR
delivery_company CR
product_company CR
proposal CRU
order CR
receive CR
receipt CR
discard CR
FastAPI 구현 및 검증 완료
```

- delivery는 purchase_item에서 user_id와 sell_product_code를 가져오거나 return에서 user_id와 inspect_code를 가져온다.
  purchase_item_code와 return_no 중 하나만 지정하며, 같은 원본 건의 중복 배송은 허용하지 않는다.
  return_no는 inspect_code + return_date(YYYYMMDD)로 구성한다.

- manager가 director에게 proposal을 작성하면 director가 대기상태인 status를 승인 또는 반려로 바꾸고 NULL이었던 director_id를 update한다.

- proposal이 승인되면 승인된 proposal에 대해서 manager가 order를 작성할 수 있다.

- order가 생성되면 그에따라 receive도 발생하게 된다.

- receipt_no는 pay_no + receipt_date(YYYYMMDD)로 자동 생성하며, receipt_amount는 접수 수량이다.
  등록 매니저는 로그인 계정, user_id는 연결된 pay에서 가져온다.

- receipt는 현재 결제완료 여부, 검수 요청과 접수 상품의 연결 관계, 누적 접수 수량 검증이 미구현 상태다.
  추후 백엔드 service에서 검증과 저장을 같은 트랜잭션으로 처리해야 한다.
  현재 검수 요청에 상품 연결 정보가 없어, 해당 관계를 확인할 근거 데이터가 필요하다.

- discard는 현재 폐기할 상품을 등록하는 것만 할 수 있고 sell_product를 지우는 실질적 폐기는 진행하지 않고 있는 상태이다.

### 검수 물품 반환

- 대리판매 등록 시 만료일(등록 + 14일)과 매니저가 지정한 반환 배송업체를 저장합니다.
  서버가 1분마다 만료된 미판매 물품을 확인해 반환·배송준비 건을 함께 생성합니다.
  거래중·거래완료 물품은 제외하며, 만료 상품 구매와 중복 반환은 차단합니다.
  기존 등록 건은 반환 배송업체를 지정해야 합니다. [대리판매 만료 반환](docs/consignment_expiry.md)

검수완료 후 사용자가 반환을 선택하면 반환 건을 자동 접수합니다.
`GET /return`, `GET /return/{return_no}`, `PATCH /return/{return_no}/manager`를 제공합니다.
return은 반환 물품·사용자·담당자만 관리하며 배송 일자·상태는 delivery에서 관리합니다.
API 및 DB 변경 내용은 [반환 문서](docs/return.md)를 참고하세요.

### Director 전용 대시보드

- Director 계정 로그인 시 전용 대시보드로 자동 이동합니다.
- Riverpod 기반으로 화면 상태와 API 요청을 관리합니다.
- 사용자, 매니저, 검수, 대리판매, 발주, 배송, 반환, 결제, 환급 및 케이스 재고의 DB 집계 지표를 표시합니다.
- 품의 목록 조회와 승인·반려 기능을 제공합니다.
- 회원 탈퇴 현황에서 사용자 ID, 닉네임, 탈퇴일, 탈퇴 종류와 작성 사유를 확인할 수 있습니다.
- 상세 통계 전용 탭에서 검수 단계별 병목·매니저 처리량·탈퇴 종류는 막대그래프로, 재고 부족·미입고 발주·지연 배송·반환 위험은 표로 확인할 수 있습니다.
- 매니저 현황과 케이스 재고 현황을 조회할 수 있습니다.

#### Director 운영 기준·상세 통계 확장

- 날짜 컬럼은 기존 프로젝트 정책대로 `DATETIME`으로 변경하지 않고 `VARCHAR(45)`를 유지합니다.
- Director 설정 화면에서 재고 부족 기준, 배송 지연 기준 일수, 검수신청 1개당 가격을 변경할 수 있습니다.
- 설정값은 `director_settings`에 저장되며 대시보드 집계와 검수비 생성에 즉시 사용됩니다.
- 상세 통계는 기간·매니저·검수 상태로 필터링할 수 있고 그래프 항목을 눌러 관련 상세 데이터로 이동할 수 있습니다.
- 통계 상세 API는 20건 단위 페이지 조회를 지원하며 CSV와 Excel(`xlsx`) 파일로 내보낼 수 있습니다.
- Director는 매니저 계정을 생성·수정·비활성화할 수 있습니다. 비활성화할 때 진행 업무가 있으면 활성 매니저에게 재배정해야 합니다.
- 관련 DB 변경은 `sql/director_operations.sql`에 정리되어 있습니다.

#### Director 기준정보 등록

- Director 화면의 `기준정보` 탭에서 케이스, 배송업체, 제조업체, 카드 카탈로그를 새로 등록할 수 있습니다.
- 케이스 코드는 기존 `case_sequence` 규칙으로 서버에서 자동 발급됩니다.
- 카드 카탈로그는 `POST /card_info`로 등록하며 판매·검수 마지막 순번은 사용자가 입력하지 않고 0부터 시작합니다.
- 카드 카탈로그 변경 권한은 전체 상품 코드에 영향을 주므로 Director 계정으로 제한합니다.

### 상품 이미지 DB 저장

- 새로 업로드한 상품 이미지는 서버 디스크가 아니라 `product_image.product_image_data`의 `MEDIUMBLOB`에 저장합니다.
- `sell_product.sell_product_image`에는 BLOB 자체가 아니라 `/media/products/{이미지ID}.{확장자}` 형식의 조회 경로를 저장합니다.
- `GET /media/products/{파일명}`은 DB에서 BLOB와 MIME 타입을 읽어 이미지 응답으로 반환합니다.
- 이미지 크기는 최대 5MB이며 JPEG, PNG, WebP 정적 이미지만 허용합니다. 저장 전에 EXIF 등 원본 메타데이터를 제거합니다.
- 전환 전에 `uploads/products`에 저장된 파일은 호환을 위해 DB에 이미지가 없을 때만 기존 파일에서 조회합니다.
- DB 생성 스크립트는 `sql/product_image_blob.sql`에 있습니다. 날짜는 프로젝트 정책대로 `VARCHAR(45)`에 저장합니다.


### 판매상품 삭제 처리

- 판매자는 본인의 판매중인 일반판매 상품을 삭제할 수 있습니다.
- `DELETE /sell_product/{sell_product_code}`는 상품을 물리적으로 삭제하지 않고 상태를 `판매취소`로 변경합니다.
- 관심상품·채팅·과거 거래 기록은 유지하며 판매취소 상품은 판매중 목록 및 판매내역 API(내 상품 관리 포함)에서 제외합니다.
- 거래중·거래완료 상품은 삭제할 수 없습니다. 기존 API 경로와 응답 형식을 유지합니다.


### 대리판매 구매·반환 배송 자동 등록

- 대리판매 상품 구매 시 구매·머니 결제·배송준비 및 최초 배송 이력을 같은 트랜잭션에서 생성합니다. 일반판매 구매에는 자동 생성하지 않습니다.
- 검수 반환 선택과 대리판매 기간 만료 반환도 배송준비 건을 자동 생성하며, 같은 원본의 중복 배송을 방지합니다.
- 관리자 반환/배송 화면에서 배송업체를 지정한 뒤 배송준비 → 배송중 → 배송완료로 처리합니다. 각 상태 변경은 `delivery_status_history`에 저장합니다.
- 추가 API: `PATCH /delivery/{delivery_no}/company`. 배송업체 미지정 상태의 배송 응답에는 업체 코드가 `null`입니다.
- DB 변경: `sql/delivery_auto_registration.sql`로 배송업체 컬럼을 NULL 허용합니다. 현재 연결 DB에는 적용했으며, 다른 환경은 별도 적용해야 합니다.
- 기존 구매·반환 전체의 자동 소급 생성은 하지 않습니다. [반환 및 배송 안내](docs/return.md)를 참고하세요.
