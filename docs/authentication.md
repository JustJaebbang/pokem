# 로그인 토큰 발급

보안 패키지는 `python -m pip install -r requirements-security.txt`로 설치합니다.
`.env`에 `JWT_SECRET_KEY`와 `ACCESS_TOKEN_EXPIRE_MINUTES`를 설정합니다.
이번 구현 환경에는 무작위 키와 만료시간 30분을 설정했습니다.
새 환경에서는 `.env.example`의 명령으로 새 키를 생성하세요.
비밀키는 공유하거나 Git에 커밋하지 않고, 서버 재시작과 여러 서버에서 같은 값을 사용합니다.
키를 교체하면 기존 토큰의 서명 검증이 실패합니다.

`POST /auth/login` 요청은 기존과 같습니다.

```json
{"login_id": "계정아이디", "password": "비밀번호"}
```

성공 응답은 기존 `role`, `account`와 함께 `access_token`, `token_type: "bearer"`,
`expires_in: 1800`을 반환합니다. 만료시간의 단위는 초입니다.
사용자·매니저·director 모두 비밀번호 해시로 검증하며, 로그인 실패 시 토큰을 발급하지 않습니다.
director도 같은 로그인 API를 사용하며 응답과 JWT의 역할은 `director`입니다.
여러 역할에서 같은 ID와 비밀번호가 인증되면 409로 거부합니다.

director는 공통 매니저 관리 권한을 포함하며, director 등록·목록·단건 조회는 director만 가능합니다.
주문(`/order`)과 입고(`/receive`)는 등록·조회 모두 매니저 전용으로 director는 접근할 수 없습니다.
매니저는 director 계정을 관리할 수 없습니다. 일반 사용자 전용 작업은 기존처럼 사용자만 가능합니다.
배송 등록·환불 등록·검수 확인처럼 `manager_manager_id`를 저장하는 작업에서
director는 실제 담당 매니저 ID를 지정해야 합니다. 생략하면 422를 반환합니다.
매니저 본인은 기존처럼 ID를 생략할 수 있으며 다른 매니저를 지정할 수 없습니다.

토큰은 HS256 서명을 사용하며 계정 ID, 역할, 발급·만료 시각, 발급자, 대상,
토큰 종류와 식별자를 포함합니다. 비밀번호·계좌·잔액은 토큰에 넣지 않습니다.
클라이언트는 이후 인증이 필요한 API에 `Authorization: Bearer <access_token>`을 보냅니다.

현재 토큰 검증과 DB 계정 조회를 기존 API에 연결했습니다.
`GET /auth/me`로 `role`과 현재 `account`를 확인할 수 있습니다.
DB에서 삭제된 계정의 토큰은 만료 전이라도 401로 거부합니다.
인증이 없거나 잘못된 경우 401, 다른 사용자의 자료나 역할에 접근하면 403을 반환합니다.

Swagger(`/docs`) 사용 순서:

1. `POST /auth/login`으로 로그인합니다.
2. 응답의 `access_token` 값을 복사합니다.
3. 상단 Authorize에 토큰 값만 붙여 넣습니다. Bearer 접두사는 자동으로 붙습니다.
4. `GET /auth/me`를 실행한 뒤 다른 기능을 검증합니다.

| API | 권한 |
| --- | --- |
| 회원가입, 로그인, 상품 목록·상세 | 공개 |
| 현재 계정 조회 | 사용자·매니저·director |
| 사용자 전체 목록, 매니저 등록·조회, 판매등록 전체 목록 | 매니저·director |
| director 등록·조회 | director |
| 사용자 상세, 구매·충전 내역 조회, 판매등록 상세 | 본인 또는 매니저·director |
| 사용자 수정·탈퇴, 관심상품 | 본인 사용자 |
| 판매상품 등록, 구매, 충전 | 로그인한 일반 사용자 |
| 판매상품 수정·삭제 | 해당 상품을 등록한 사용자 |

관리자 등록도 기존 관리자의 토큰이 필요합니다. 최초 관리자 계정은 별도의 관리 절차로 준비해야 합니다.

구매·충전·관심상품 추가에서 `user_user_id`는 생략할 수 있습니다.
서버는 실제 처리할 사용자 ID를 토큰에서 확인한 계정으로 설정합니다.
기존처럼 사용자 ID를 전송할 경우 본인과 다른 ID는 403으로 거부합니다.
판매상품 등록의 임시 `user_id` 쿼리 파라미터는 제거했습니다.
사용자 수정·탈퇴 및 관심상품 조회·해제의 기존 경로는 유지하며 본인 ID만 허용합니다.
구매·충전 목록의 `user_id`를 생략하면 본인 목록을 반환합니다.
관리자가 다른 사용자의 구매·충전 목록을 조회할 때는 `user_id`를 지정합니다.

`POST /purchase_item` 또는 `POST /wishlist`:

```json
{"sell_product_sell_product_code": "판매상품코드"}
```

`POST /recharge`:

```json
{"recharge_account": "충전계좌", "recharge_price": 10000}
```

충전 API의 실제 입금·결제 승인 확인은 아직 연동되지 않았습니다.
인증은 본인 확인이며 결제 승인을 대신하지 않습니다.
refresh token과 로그아웃에 의한 즉시 폐기 기능도 아직 없습니다.
만료 후에는 다시 로그인해야 합니다.

### 회원탈퇴 연결

Flutter의 나 → 회원탈퇴에서 잔액 조회, 선택 사유(200자), 동의 및 최종 확인 후 기존 DELETE API를 호출합니다. 서버는 사용자 행 잠금 안에서 `user_money == 0`을 검사하고, `user` 및 거래내역을 삭제하지 않고 `quit`에 탈퇴 일시·사유만 기록합니다. quit 기록이 있으면 사용자 로그인과 기존 토큰 인증을 거절하고 WebSocket 인증·메시지 저장에서도 차단합니다. user ID가 남아 있으므로 동일 ID 재가입은 허용하지 않습니다. 탈퇴 중복 검사는 사용자 행 잠금 안에서 수행합니다. 성공 시 저장된 인증정보와 메모리 세션을 정리합니다. 결과가 불명확하면 삭제 요청을 반복하지 않고 계정 조회로 확인하며, 401/404를 탈퇴 성공으로 해석하지 않습니다.

### 프로필 이미지 필드

`user` 테이블에 `user_profile_image VARCHAR(1000) NULL`을 추가했습니다. 현재 연결 DB는 적용 완료이며 별도 DB는 `sql/user_profile_image.sql`을 컬럼이 없을 때 최초 한 번 실행합니다.

회원가입 요청과 사용자 조회·로그인·인증 응답에서 이미지 URL을 선택 필드로 지원합니다. `PUT /user/{user_id}`에서는 생략 시 기존 사진 유지, null이면 기본 이미지, 기존 업로드 API에서 받은 `/media/products/{uuid}.{jpg|png|webp}` URL이면 해당 사진으로 변경합니다. 연락처·이메일·주소의 기존 수정 필드는 유지합니다. 업로드는 기존 인증된 `POST /sell_product/image`를 그대로 사용하며 소유 사용자 검사는 기존 회원정보 수정 라우터를 따릅니다.
