# 상품 문의 채팅

채팅방 생성·목록·이전 대화 조회는 HTTP, 실시간 전송·수신은 WebSocket을 사용합니다.
기존 HTTP 메시지 전송도 유지하며 저장 후 같은 방의 WebSocket 연결에 전달합니다.
푸시 알림, 읽음 표시, 이미지 전송, 방 나가기/종료 API는 아직 포함하지 않았습니다.

## 검증 순서

1. 판매자가 상품을 등록합니다.
2. 다른 사용자가 로그인하고 `POST /chat_room`에 상품 코드를 보냅니다.

```json
{
  "sell_product_sell_product_code": "상품코드"
}
```

문의자는 토큰, 판매자는 판매등록에서 서버가 결정합니다. 임의의 참여자 ID를 보내면 422입니다.
본인 상품 문의는 409입니다. 새 방은 판매중인 상품에만 생성됩니다.
신규 생성은 201, 같은 상품에 같은 문의자가 재요청하면 기존 방과 200을 반환합니다.
다른 문의자는 별도 방을 갖고, 판매자는 두 방을 모두 자신의 목록에서 볼 수 있습니다.
기존 방은 상품이 거래중·거래완료로 바뀌어도 조회하고 대화할 수 있습니다.
방 ID는 VARCHAR(45)에 맞춰 CR_와 UUID를 조합하여 생성합니다.

3. 응답의 `chat_room_id`로 `POST /chat_room/{room_id}/messages`를 실행합니다.

```json
{
  "chat_contents": "안녕하세요. 직거래 가능한가요?"
}
```

`chat_type`은 생략하면 text입니다. 현재 text만 허용합니다.
내용은 공백만 아닌 1~500자이며 발신자와 시각은 서버가 설정합니다.
중복 요청을 보내면 별도 메시지가 저장됩니다. 재전송 중복 방지는 아직 포함하지 않았습니다.

4. 판매자로 로그인하고 `GET /chat_room`에서 방을 찾습니다.
5. 같은 메시지 전송 API로 답장합니다.
6. 양쪽 모두 `GET /chat_room/{room_id}/messages`로 대화를 조회합니다.

## 조회 API

| API | 동작 |
| --- | --- |
| `GET /chat_room?limit=50&offset=0` | 내가 문의자 또는 판매자인 방 목록. 생성일 내림차순 |
| `GET /chat_room/{room_id}` | 참여 중인 방 상세 |
| `GET /chat_room/{room_id}/messages?after_chat_seq=0&limit=50` | 해당 방의 메시지를 오래된 순서로 조회 |

limit은 1~100입니다. 다음 메시지는 받은 마지막 chat_seq를 after_chat_seq에 넣어 조회합니다.
예를 들어 마지막 순번이 23이면 `after_chat_seq=23`으로 이후 메시지를 조회합니다.
재접속 시 마지막으로 받은 순번 이후를 이 API로 조회하여 누락 메시지를 복구합니다.
메시지 시간은 DB 세션을 UTC로 고정해 저장·조회하고 응답에 UTC 오프셋을 포함합니다.
앱에서 한국 시간으로 표시하려면 Asia/Seoul로 변환합니다.
채팅방 생성일은 기존 문자열 컬럼에 한국 시간(+09:00)으로 저장합니다.

## 권한과 상태

모든 API에 일반 사용자 토큰이 필요합니다. 채팅방의 문의자·판매자만 방 상세 및 메시지를 조회·전송합니다.
관리자 계정에 일반 대화 열람 권한을 부여하지 않았습니다.
종료된 방은 기존 메시지를 읽을 수 있지만 전송은 409로 거부합니다.
대화중/종료 상태는 상품 판매 상태와 별개입니다.

`python tests/verify_chat_db.py`로 실제 DB·JWT를 사용하는 상품 조회 → 문의방 생성 →
양방향 WebSocket 전송 → HTTP 메시지의 실시간 전달 → 대화 조회를 검증했습니다.
방 재사용, 참여자 권한, 잘못된 메시지 거부와 순번 기준 재조회도 확인했습니다.
테스트 방·메시지는 종료 시 해당 기록만 정리하며 기존 대화는 유지합니다.
AUTO_INCREMENT 순번은 되돌리지 않습니다. 여러 서버 간 전달과 동시 부하 검증은 포함하지 않습니다.
DB 구조는 `sql/chat_room_participants.sql`에 있으며 이미 적용되어 있으므로 다시 실행하지 않습니다.


## WebSocket 사용법

서버 실행 환경에 필요하면 `python -m pip install -r requirements-chat.txt`로 WebSocket 지원을 설치합니다.
현재 전달 관리자는 서버 프로세스 메모리를 사용하므로 `uvicorn main:app --workers 1`로 운영합니다.
여러 worker/서버를 사용할 경우 Redis 등의 공유 전달 계층을 추가해야 합니다.
서버 재시작 시 연결은 끊어지며, 저장한 메시지는 DB에 유지됩니다.

1. HTTP `POST /chat_room`으로 방을 생성하거나 기존 방 ID를 받습니다.
2. `ws://서버주소:포트/chat_room/{room_id}/ws`에 연결합니다. HTTPS 환경은 wss://를 사용합니다.
3. 브라우저에서는 연결 후 10초 안에 첫 프레임으로 다음 JSON을 보냅니다.

```json
{"type": "auth", "access_token": "로그인 응답에서 받은 토큰"}
```

모바일 앱이나 Postman은 연결 요청에 `Authorization: Bearer <토큰>` 헤더를 지정할 수도 있습니다.
헤더가 있으면 첫 auth 프레임은 보내지 않습니다. 토큰을 URL 쿼리에 넣는 방식은 지원하지 않습니다.
인증 성공 시 서버는 먼저 `{"type":"ready","room_id":"...","user_id":"..."}`를 보냅니다.
그 뒤 텍스트 메시지를 전송합니다.

```json
{"chat_contents": "안녕하세요"}
```

저장 성공 시 발신자를 포함한 같은 방의 연결 모두 아래 이벤트를 받습니다.

```json
{
  "type": "message",
  "data": {
    "chat_seq": 1,
    "chat_type": "text",
    "chat_contents": "안녕하세요",
    "chat_time": "2026-10-29T00:00:00Z",
    "chat_room_chat_room_id": "CR_...",
    "user_user_id": "문의자아이디"
  }
}
```

DB 저장이 실패하면 방송하지 않고 발신자에게 error 이벤트를 보냅니다.
422(내용 오류)·409(종료된 방) 등의 error 이벤트 후에는 내용을 고쳐 다시 보낼 수 있습니다.
401·403·404는 error 후 연결을 1008로 종료합니다. 크기 초과는 1009, 내부 연결 오류는 1011입니다.
토큰 만료와 탈퇴·참여 권한은 전송/수신 시 확인하며 유휴 연결도 최대 30초 간격으로 재확인합니다.
만료 후 새 토큰으로 재접속하세요.

오프라인 사용자에게 푸시를 보내지는 않습니다. 재접속하면 HTTP after_chat_seq 조회를 이용합니다.
이미 저장된 메시지의 전송 응답을 받지 못했더라도 저장은 완료되었을 수 있으므로,
재접속 후 이력을 먼저 확인하고 메시지 chat_seq로 중복 수신을 제거하세요.
아직 클라이언트 요청 ID를 통한 메시지 재전송 중복 방지는 없습니다.

### 브라우저로 검증

`scripts/chat_websocket_client.html`을 브라우저에서 열 수 있습니다.
서버 주소는 현재 FastAPI 실행 주소로 바꾸세요.
방을 생성한 뒤 문의자·판매자 토큰으로 두 창에서 같은 room_id에 연결하고 메시지를 주고받습니다.
토큰은 테스트 페이지에서 브라우저 저장소나 로그에 저장하지 않습니다.
Swagger는 HTTP 검증에 사용하고 WebSocket 검증은 이 파일 또는 Postman으로 진행합니다.

실시간 전달 테스트는 별도 테스트 DB를 사용했으며 실제 DB에는 테스트 메시지를 저장하지 않았습니다.
