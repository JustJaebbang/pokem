# 검수 물품 반환 및 배송

사용자가 검수완료 물품에 반환을 선택하면 `return`과 `delivery`를 같은 트랜잭션에서 생성합니다.
판매상품 등록 없이 검수 코드로 연결하며, 검수 물품당 반환 한 건·반환당 배송 한 건만 허용합니다.
같은 선택을 다시 요청해도 중복 생성되지 않고, 배송·이력 저장 실패 시 선택과 반환도 함께 롤백됩니다.
반환번호는 `RET_` + UUID의 32자리 hex입니다.

## 배송 흐름

1. 반환 선택 → 반환접수 및 배송준비 건 자동 생성.
2. 배송 담당 매니저가 배송업체 지정.
3. 배송 시작 → `delivery.delivery_status=배송중`.
4. 배송 완료 → `delivery.delivery_status=배송완료`.

일자와 배송 진행의 기준은 `delivery`이며, 최초 등록과 각 상태 변경은 `delivery_status_history`에 기록합니다.
기존 호환용 `return.return_status`는 반환접수/배송대기/배송중/반환완료로 관리하고, 배송중·반환완료는 배송 상태 전환 시 자동 반영합니다.
반환 담당자 배정은 선택적으로 유지하며, 자동 배송의 초기 담당자는 해당 검수를 완료한 매니저입니다.
자동 등록 이력의 메모로 자동 생성임을 구분하며, 배송업체 지정 시 실제 배송 담당자로 갱신합니다.

대리판매 기간 만료로 발생한 반환도 같은 자동 등록 경로를 사용합니다. 배송업체는 생성 후 지정합니다.

## API

모든 요청에 Bearer 토큰이 필요합니다.

| API | 권한 | 동작 |
| --- | --- | --- |
| `PUT /inspect/{inspect_code}/choice` | 신청자 | 반환 선택 시 반환 및 배송 자동 생성 |
| `GET /return?inspect_code=검수번호&limit=20&offset=0` | 사용자·매니저 | 사용자는 본인 반환만 조회 |
| `GET /return/{return_no}` | 사용자·매니저 | 타인 또는 없는 반환은 사용자에게 404 |
| `PATCH /return/{return_no}/manager` | 매니저 | 로그인 매니저 배정. 본문 `{}` |
| `PATCH /delivery/{delivery_no}/company` | 매니저 | 배송준비 상태에서 업체 지정 |
| `PATCH /delivery/{delivery_no}/status` | 매니저 | 배송준비 → 배송중 → 배송완료 |
| `GET /delivery/status-history?delivery_no=배송번호` | 매니저 | 단계별 처리 이력 조회 |

배송업체 지정 본문은 `{"delivery_company_delivery_company_code":"업체코드"}`입니다.
상태 변경 본문은 `{"delivery_status":"배송중","memo":"택배사 인계"}`이며 메모는 선택입니다.
배송업체 미지정, 역순 변경, 배송준비에서 배송완료로 건너뛰기는 409입니다.
같은 상태 재요청은 중복 이력을 만들지 않습니다.

## DB 및 적용 범위

기존 반환 구조를 사용하는 DB 기준으로 `sql/delivery_auto_registration.sql`을 적용합니다.
배송업체 컬럼만 NULL 허용으로 변경하고, 구매/반환 연결의 고유키와 외래키는 유지합니다.
새로 발생한 반환부터 자동 등록합니다. 기존 반환 데이터 전체를 임의로 변환하지 않습니다.
기존 미등록 건은 관리자 `POST /delivery`로 등록할 수 있습니다.
이전 반환 구조 전환 SQL은 현재 DB 상태를 확인하지 않고 재실행하지 마세요.
